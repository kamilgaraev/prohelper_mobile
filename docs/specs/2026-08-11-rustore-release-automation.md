# Автоматический выпуск мобильного приложения МОСТ в RuStore

## Цель

Автоматизировать сборку подписанного Android App Bundle, создание версии в RuStore и отправку на модерацию. Фактическая публикация должна запускаться отдельно после успешной модерации и явного подтверждения в защищённом GitHub Environment.

## Границы задачи

В задачу входят:

- GitHub Actions для проверки и отправки релиза по Git-тегу;
- GitHub Actions для ручной публикации версии после модерации;
- изолированный клиент RuStore Public API;
- безопасное восстановление Android keystore только на временном runner;
- проверка формата версии, статусов RuStore и ответов API;
- тесты скриптов релиза без обращения к реальному RuStore.

В задачу не входят изменение Flutter-функциональности, миграция ключа подписи, первая ручная публикация приложения и автоматическое исправление деклараций чувствительных разрешений.

## Точка запуска и версия

Отправка на модерацию запускается только тегом формата `android-v<versionName>+<versionCode>`, например `android-v1.2.0+42`.

Workflow перед сборкой проверяет:

- тег соответствует ожидаемому формату;
- `versionCode` является положительным целым числом;
- версия из тега передаётся Flutter через `--build-name` и `--build-number`;
- обязательные секреты и переменные заданы;
- для одного тега одновременно выполняется не более одного релизного workflow.

## Компоненты

### Workflow отправки

`rustore-submit.yml` выполняет следующие шаги:

1. Получает исходный код тега.
2. Устанавливает закреплённую стабильную версию Flutter и зависимости.
3. Запускает форматирование, статический анализ и тесты.
4. Восстанавливает keystore и `android/key.properties` из секретов окружения.
5. Собирает подписанный AAB.
6. Получает короткоживущий JWE-токен RuStore.
7. Создаёт черновик с типом публикации `MANUAL`.
8. Загружает AAB и отправляет версию на модерацию.
9. Сохраняет безопасное резюме с `versionId`, но не секреты и не токены.

### Workflow публикации

`rustore-publish.yml` запускается вручную с обязательным `versionId`. Job использует Environment `rustore-production`, проверяет, что версия имеет статус `READY_FOR_PUBLICATION`, после чего вызывает ручную публикацию. Повторный запуск для уже активной версии завершается без повторной публикации.

### Клиент RuStore

Скрипт клиента находится отдельно от YAML и предоставляет команды:

- `submit` — авторизация, создание черновика, загрузка AAB, отправка на модерацию;
- `publish` — авторизация, проверка статуса и публикация.

Клиент использует только стандартную библиотеку Python и системный `openssl` для RSA SHA-512 подписи. HTTP-ответ считается успешным только при допустимом HTTP-коде и поле `code: OK`. Техническая ошибка выводится без токенов, приватного ключа и паролей подписи.

## Секреты и доступы

Используется GitHub Environment `rustore-production` со следующими секретами:

- `RUSTORE_KEY_ID`;
- `RUSTORE_PRIVATE_KEY`;
- `ANDROID_KEYSTORE_BASE64`;
- `ANDROID_KEY_ALIAS`;
- `ANDROID_KEY_PASSWORD`;
- `ANDROID_STORE_PASSWORD`.

Переменная окружения: `RUSTORE_PACKAGE_NAME`.

Workflow получает минимальные права GitHub: `contents: read`. Секреты не передаются workflow из pull request и не сохраняются в artifacts. Временные файлы подписи создаются только внутри runner и удаляются после работы.

## Ошибки и повторные запуски

- При ошибке до создания черновика workflow завершается без изменений в RuStore.
- При ошибке после создания черновика workflow сообщает `versionId`; черновик можно удалить вручную или отдельной командой обслуживания.
- При новых чувствительных разрешениях RuStore отклоняет API-загрузку; декларация заполняется вручную в консоли.
- Сетевые запросы чтения и авторизации допускают ограниченные повторы. Создание черновика, отправка на модерацию и публикация автоматически не повторяются, чтобы не дублировать операции.
- Короткоживущий JWE получается заново в каждом workflow.

## Проверка

- Unit-тесты разбора релизного тега и ответов RuStore.
- Unit-тесты формирования сообщения для RSA-подписи и обработки статусов.
- Статическая проверка YAML и актуальности используемых GitHub Actions.
- Локальная проверка Python-синтаксиса и тестов без реальных секретов.
- Первый реальный запуск выполняется на новой версии с ручной публикацией после проверки черновика в RuStore.

## Критерии готовности

- Тег создаёт подписанный AAB и отправляет соответствующую версию на модерацию.
- Публикация невозможна до статуса `READY_FOR_PUBLICATION`.
- Никакие секреты не попадают в репозиторий, artifacts и логи.
- Ошибки API завершают workflow с понятной диагностикой и известным `versionId`, если он уже создан.
