# Инструкции репозитория мобильного приложения МОСТ

## Область действия

- Эти правила действуют во всём репозитории. Более вложенный `AGENTS.md` может уточнять их для своей директории.
- Продукт называется **МОСТ**. `prohelpers_mobile` — только техническое имя репозитория.
- Всегда общайся на русском языке. Пользовательские тексты должны быть понятными, естественными и не содержать внутренних технических терминов.
- Учитывай существующие инструкции `.agent/rules/`, если они не конфликтуют с этим файлом и прямым запросом пользователя.

## Коммиты и Pull Request

- Заголовки коммитов и PR пиши по-русски в формате `type[scope]: описание`. Типы: `fix`, `feat`, `refactor`, `test`, `docs`, `chore`. В `scope` указывай функциональную область (`договоры`, `акты`, `отчёты`); общее название интерфейса используй только для изменений без одной функциональной области.
- Описание PR заполняй по русскому шаблону `.github/pull_request_template.md`: зачем изменение, что сделано, что фактически проверено, риски и действия при выпуске. Для бага добавляй причину; `Closes #...` — только при существующей задаче. Не оставляй пустые подсказки.
- При разрешённом слиянии используй `Squash and merge` и проверь итоговое сообщение коммита. Автоматическое англоязычное резюме Bito в описание PR не добавляй; `.bito.yaml` отключает `post_description`.

## Git, безопасность и окружение

- Не работай напрямую в `main`: обновляй его только fast-forward, создавай отдельную ветку и передавай изменения через Pull Request.
- Не коммить, не push, не создавай PR, не merge и не публикуй приложение без отдельной явной команды. Не изменяй и не откатывай чужие файлы.
- Перед правками проверяй ветку и `git status`. Не используй `git reset --hard`, принудительный checkout, широкое рекурсивное удаление или очистку неотслеживаемых файлов без прямого разрешения.
- Не изменяй CI/CD, GitHub Actions, signing и deployment-конфигурацию без отдельного запроса.
- Не добавляй `.env`, ключи подписи, provisioning profiles, токены, пароли, production-данные, локальные пути пользователя, логи, кеши, `.dart_tool`, `build`, platform-generated secrets и зависимости.
- Не создавай SSH-ключи и не предполагай production-доступ. Production-диагностика возможна только после отдельной явной выдачи владельцем read-only доступа для конкретной задачи; операции записи и раскрытие секретов запрещены.
- Не запускай приложение, эмуляторы, dev-серверы или сборки без необходимости и согласования. Для документальных правок не запускай сборки и тесты.

## Архитектура Flutter/Dart

- Следуй sound null safety, Dart style guide и `flutter_lints`. Сохраняй feature-first структуру и границы Clean Architecture.
- Используй композицию widgets и `const`-конструкторы. Разделяй presentation, state/application, domain и data; UI не должен напрямую выполнять сетевые запросы или содержать бизнес-правила.
- Используй существующий в feature способ управления состоянием; для сложной логики предпочитай принятый в проекте Riverpod. Не смешивай Provider, Riverpod и Bloc в одном сценарии без архитектурной причины.
- Backend остаётся источником бизнес-правил, permissions, ownership и валидации. Мобильные guards и скрытие UI не заменяют серверную авторизацию.
- Используй DTO для API, repository для доступа к данным и явное преобразование transport-моделей в domain/presentation-модели.

## UI, API, права и переводы

- Используй `Theme.of(context)` или `MostTheme`; не хардкодь theme-dependent цвета и стили.
- Обрабатывай loading, error, empty, offline/timeout и success-состояния. Для длинных списков используй lazy builders; учитывай слабые устройства, медленную сеть, retry и защиту от повторных действий.
- Обеспечивай `Semantics`, масштабирование текста, контраст, корректные touch targets и платформенно ожидаемую навигацию.
- Используй типизированный контракт Mobile API и проверяй роли/permissions, полученные от backend. При несовпадении payload исправляй согласованный контракт, а не скрывай проблему неявными fallback-ами.
- Пользовательские сообщения должны проходить через существующий механизм локализации. Не показывай ключи переводов, permission slug-и, stack traces или технические ошибки; русский текст сохраняй в корректной UTF-8.

## Проверки

- Для документации и текстов без изменения поведения не запускай сборку и тесты; проверь diff, Markdown, UTF-8 и отсутствие секретов.
- После изменений Dart запускай форматирование и статический анализ только для затронутых файлов или минимального модуля.
- При изменении бизнес-логики, providers, навигации, API-контрактов, permissions или сложных состояний добавляй и запускай целевые unit/widget/integration-тесты. Воспроизводимый баг защищай регрессионным тестом.
- Не запускай полную mobile-сборку без прямого запроса пользователя.
- В итоговом ответе перечисли изменённые файлы, выполненные проверки и причины пропуска остальных.
